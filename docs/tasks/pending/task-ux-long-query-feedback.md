# Улучшение обратной связи при длительной обработке запросов

**Статус**: 📋 Запланировано  
**Приоритет**: 🟡 Средний  
**Категория**: Улучшения UX

## Описание

При отправке запроса, который требует длительной обработки (cursor-agent думает, ищет по файлам, обращается к API), пользователь видит только статичное сообщение «⏳ Обрабатываю запрос...» без понятного прогресса, времени ожидания и явной отмены. При сбоях или сетевых ошибках обратная связь слабая.

Нужно: **таймер в статусе**, **явная кнопка «Отменить»**, **понятные сообщения об ошибках** (в т.ч. при таймауте), **параллельная работа в нескольких сессиях** без путаницы ответов.

## Цели

1. Дать пользователю визуальную обратную связь о ходе обработки (время, при необходимости сброс таймера после начала стриминга).
2. Дать возможность **явно отменить** долгий запрос (kill процесса `cursor-agent`).
3. **Не ломать** длинные «размышления» Cursor без вывода: см. раздел про таймауты ниже.
4. Улучшить диагностику: stderr, логирование этапов, при необходимости — показ пользователю краткой ошибки.
5. Спроектировать поведение при **нескольких активных сессиях** и **ответах не в порядке отправки**.

## Как сейчас устроены таймауты (`cursor_cli_service.process_query`)

Переменные окружения:

| Переменная | По умолчанию | Смысл |
|------------|--------------|--------|
| `CURSOR_CLI_TIMEOUT` | `600` | Максимум секунд **одного** ожидания `stdout.read(4096)` **до появления первого непустого вывода** (пока `first_chunk_time` ещё нет). Это не «общий лимит 10 минут на весь ответ», а **лимит тишины до первого байта** в потоке. |
| `CURSOR_CLI_IDLE_TIMEOUT` | `30` | После **первого** непустого чанка каждое следующее чтение ждёт не больше столько секунд **тишины между чанками**. Если дольше нет данных — считаем, что вывод закончился, процесс завершают (SIGTERM и т.д.). |

Итого:

- **Долгое «мышление» без вывода** (нет первого чанка): каждый цикл `read` может ждать до `CURSOR_CLI_TIMEOUT` секунд. Уменьшение дефолта с 600 до 180–300 **укоротит** допустимое молчание до первого вывода — **риск оборвать тяжёлые запросы (5+ минут без stdout)**.
- **После начала стриминга** лимит «думает» не 600 с, а **паузы между порциями вывода** — по `CURSOR_CLI_IDLE_TIMEOUT` (30 с). Если модель редко шлёт чанки реже чем раз в 30 с, теоретически возможен преждевременный выход (это отдельный edge case).

**Рекомендация по продукту:** не снижать `CURSOR_CLI_TIMEOUT` «всем по умолчанию» без явной настройки; в задаче — **показывать пользователю прошедшее время** и **отмену**; при желании — вынести в `.env` комментарий «для терпеливых запросов оставьте 600+». Опционально: отдельная настройка «макс. ожидание первого чанка» vs «idle между чанками» уже есть двумя переменными — задокументировать в README/docs.

## Задачи

### Таймер и текст статуса

- [ ] Периодически обновлять сообщение «⏳ Обрабатываю запрос...» с прошедшим временем (например каждые 15–30 с): «⏳ … (45 с)», «⏳ … (2 мин)».
- [ ] Реализовать фоновую задачу (`asyncio.create_task`) + `asyncio.Event` для остановки при завершении запроса.
- [ ] После **первого чанка** стриминга (если включён стриминг): либо остановить таймер «ожидание», либо переключить текст на «⏳ Получаю ответ...» — зафиксировать выбранный UX в реализации.

### Кнопка «Отменить»

- [ ] Inline-кнопка «❌ Отменить» у сообщения со статусом.
- [ ] Callback: найти активный `cursor-agent` для **этой** операции (см. корреляцию ниже), `process.kill()` / аккуратный SIGTERM по политике как в `process_query`.
- [ ] Ответ пользователю: «Обработка отменена»; не падать, если процесс уже завершился.
- [ ] Хранить ссылку на subprocess или token отмены **в контексте конкретного запроса** (не только `user_id`), чтобы не отменить чужой запрос в другой сессии.

### Ошибки и таймаут

- [ ] При `TimeoutError` до первого чанка — сообщение с понятным текстом (повторить запрос, упростить, проверить сеть), без сырого traceback в Telegram.
- [ ] Опционально: при ошибке процесса (код ≠ 0) — кратко показать хвост stderr в логах; в Telegram — обезличенно.

### Диагностика и стабильность

- [ ] Читать **stderr** параллельно с stdout (отдельная `asyncio.Task`), чтобы избежать заполнения pipe (~64 КБ) и deadlock.
- [ ] Логи: «процесс запущен», «первый чанк через N с», «idle M с», «таймаут до первого вывода».

### Параллельные сессии и ответы «не по порядку»

Сейчас пользователь может переключать **активную сессию** и слать запросы в разные контексты. Если два запроса обрабатываются **асинхронно** (два долгих `process_query`), ответ от **первой** сессии может прийти **позже**, чем пользователь уже пишет во **второй** — нужно избежать путаницы.

Варианты дизайна (выбрать при реализации):

1. **Строгая очередь на пользователя:** пока не завершён запрос в сессии A — не стартовать запрос в сессии B (сообщение «Дождитесь ответа по сессии #…»). Просто, но хуже UX.
2. **Параллельно + жёсткая корреляция:** каждый ответ уходит **reply** на своё сообщение «⏳ Обрабатываю…» или с префиксом «[Сессия #N]» и `reply_to_message_id` на исходный запрос пользователя.
3. **Трекинг `processing_message_id` + `session_id`:** в БД или in-memory карта `(user_id, session_id) → asyncio.Task + process`, отмена и финализация только по совпадению.

- [ ] Зафиксировать выбранную модель в коде и в `handlers/messages.py` / `query_processing_service.py`.
- [ ] Протестировать: два быстрых запроса в разных сессиях; долгий + короткий с переключением активной сессии.

## Технические детали

### Текущий flow обработки запроса

```
Пользователь → Telegram → bot (aiogram)
  → QueryProcessingService.process_query()
    → typing_message = "⏳ Обрабатываю запрос..."
    → CursorCLIService.process_query()
      → asyncio.create_subprocess_exec("cursor-agent", ...)
      → цикл чтения stdout:
            до первого непустого чанка: read_timeout = CURSOR_CLI_TIMEOUT
            после первого чанка: read_timeout = CURSOR_CLI_IDLE_TIMEOUT
      → стриминг через on_chunk (если включён)
    → отправка ответа пользователю
```

### Deadlock stderr

Stdout и stderr в `PIPE`; stderr сейчас дочитывается в основном после цикла stdout. При большом stderr возможен блокирующий `write` в дочернем процессе. Решение: параллельная задача чтения stderr.

### Пример фона таймера (черновик)

```python
async def _update_typing_timer(self, typing_message, cancel_event: asyncio.Event):
    start = time.time()
    while not cancel_event.is_set():
        await asyncio.sleep(15)
        if cancel_event.is_set():
            break
        elapsed = int(time.time() - start)
        # форматирование elapsed → текст
        try:
            await typing_message.edit_text(f"⏳ Обрабатываю запрос... ({elapsed}с)", ...)
        except Exception:
            pass
```
