# Отображаемый заголовок сессии (числовой ID + «имя» чата)

**Статус**: 📋 Запланировано  
**Приоритет**: 🟡 Средний  
**Категория**: Улучшения UX (бот, Mini App, главное меню)

## Описание

Сейчас сессии в боте идентифицируются в основном по **номеру** (`session_id`), что при большом количестве сессий и переключениях между ними создаёт путаницу. В интерфейсе Cursor чатам часто присваивается **понятное название** (автоматически после начала диалога или вручную). Нужно понять, можно ли **получить именно этот заголовок** из Cursor/CLI и использовать его в боте; если нет — зафиксировать **эквивалентное поведение на стороне бота** (сохраняя числовой ID везде, где он нужен).

### Дополнительно: что пишут в сети про SQLite Cursor (неофициально)

Это **не документация Cursor**, а разборы и скрипты сообщества; схема может измениться в любой апдейт.

- В статьях и обзорах локального хранилища (например, разборы `~/.cursor/chats/.../store.db`) описывают **метаданные сессии** с полями вроде `agentId`, **`name` (подпись как заголовок чата)**, `mode`, `createdAt`, `lastUsedModel` и ссылками на блобы сообщений. Идея: заголовок **может физически присутствовать** в локальной БД рядом с `chatId`, но **формат таблиц/JSON внутри SQLite не зафиксирован публично**.
- Встречаются также проекты экспорта из **`state.vscdb`** / `workspaceStorage` (VS Code/Cursor), отдельные gists со скриптами извлечения — это другой слой хранения, тоже без гарантий стабильности.
- **На сервере бота** путь к `store.db` известен, если используется тот же volume, что и для CLI (`<workspace-hash>/<cursor_chat_id>/store.db`). Теоретически можно попробовать **прочитать `name` после первого ответа**, сопоставив с `cursor_chat_id`. Минусы: хрупкость, необходимость парсить внутренности, отсутствие SLA от Cursor, усложнение кода и отладки.

**Итог по SQLite на текущий момент (без прогноза на будущие версии):** оснований утверждать «заголовка **точно нет**» в файловой системе — мало; наоборот, **эвристика сообщества** — что метаданные чата с **именем** лежат локально. Но для продукта это остаётся **недокументированным** каналом: для стабильного UX разумно опираться на **собственный заголовок в БД бота**, а чтение `store.db` — только опциональный эксперимент / best-effort sync.

**Вывод для продукта:** через **официальный CLI/API** заголовок **не отдаётся** (есть UUID). Через **локальный SQLite** заголовок **вероятно извлекаем**, но без гарантий. Для предсказуемого поведения бота — **генерация заголовка у нас** (ниже).

## Рекомендуемый подход: короткий LLM-заголовок (как полировка голоса)

Раз уж **стабильного API** на заголовок нет, логично после первого Q&A выставлять `display_title` **самим**:

1. **Не путать с Whisper:** распознавание голоса — **Whisper** (аудио → текст). Отдельно уже есть **лёгкая постобработка** транскрипции через `CursorCLIService.run_simple_prompt()` и **`TRANSCRIPTION_POLISH_MODEL`** (`config.TRANSCRIPTION_POLISH_MODEL`, по умолчанию `auto`) — см. `services/transcription_service.py`.
2. **Для заголовка сессии** разумно использовать **тот же класс вызовов** (короткий промпт, маленький вывод, ограничение по длине), чтобы не раздувать расход: по сути **один запрос** «3–8 слов, без кавычек, по сути первого диалога» на основе первого пользовательского сообщения (и при желании краткой выжимки ответа).
3. Опционально вынести в конфиг отдельную переменную, например **`SESSION_TITLE_MODEL`**, с **дефолтом = `TRANSCRIPTION_POLISH_MODEL`**, чтобы не плодить настройки без нужды.
4. Fallback при ошибке/отключении: обрезка первого пользовательского сообщения до N символов (как у многих UI).

Опционально позже: **best-effort** чтение `name` из `store.db` по `cursor_chat_id` — только если команда захочет терпеть хрупкость и тестировать на каждой версии CLI.

## Цели

1. Не терять **числовой идентификатор** сессии в системе (FK, API, логика); заголовок — **дополнение**, не замена ID.
2. После **первого промпта и первого ответа** выставлять **отображаемый заголовок** сессии (если ещё не задан вручную — см. ниже).
3. В **Mini App**: в списке сессий показывать **номер и заголовок** (когда есть); при отсутствии заголовка — как сейчас или краткий плейсхолдер.
4. В **главном меню** / блоке «активная сессия»: показывать **«Сессия N»** и **заголовок**, если он уже известен.

## Технические детали

- Связь с Cursor CLI: поле `cursor_chat_id` остаётся для `--resume`; заголовок в UI Cursor и заголовок в боте **могут различаться** — это ожидаемо, если нет официального API.
- Если в будущем появится стабильный способ синхронизировать с IDE — можно добавить второй этап без ломки числового `session_id`.
